# 网易云音乐歌手专辑监控 · cloudmusic-artist-album-monitor

> 这个爬虫是写来给我自己用的，自己关心的艺人是越来越多了，每天都一个个点开艺人页去检查有没有新歌或者翻唱被传上来实在是太麻烦了，之前试过用bat文件但是一瞬间开一堆网页特别卡，有几率被ban还对CPU有害，于是就写了这玩意（我以前怎么没想到用爬虫呢，真的还是笨了）

## 它做什么

按 `歌手配置.txt` 里的名单，用网易云音乐的公开 API 抓取每位歌手的**全部专辑**，
再和上一次成功抓取的快照按**专辑ID**对比，把**新增**与**下架**记录追加到日志里。

跑一次 = 得到一份最新快照 + 一份只记录变化的日志，不用再一个个点开歌手页翻列表。

## 功能特性

- 单文件脚本，只用 `requests`，同步顺序请求；不用异步、不用多线程、不用 Selenium
- 自动翻页，抓全一位歌手的全部专辑（不受网页上“只展示前面若干张”、要登录的限制）
- 用**专辑ID**判断新增，歌手改专辑名、改版、换封面都不会被误判成新专辑
- 抓取失败或歌手ID无效时**绝不清空旧快照**，只更新状态与失败原因
- 网络类错误自动重试；失败之后再次成功时，会补记这段时间的新增并写一条 `[恢复]`
- 请求之间随机延时，避免高频访问给自己惹麻烦
- 快照原子写入（先写临时文件再替换），中途 Ctrl+C 也不会写坏 JSON
- 零配置、无数据库，三个数据文件都在脚本同目录

## 快速开始

1. 安装依赖：`pip install requests`
2. 编辑 `歌手配置.txt`，一行写一位歌手：`歌手名 | 歌手ID`
3. 运行：

```bash
python 专辑监控.py
```

歌手ID 就是歌手主页地址 `https://music.163.com/#/artist/album?id=53678173` 里的那串数字。
第一次运行会把抓到的所有专辑都记为 `[新增]`。

## 配置格式

```text
LIMIT = 50            # 每页抓取条数，可以不写，默认 50

# 歌手名 | 歌手ID
花譜 | 32062601
理芽 | 47614811
```

- 以 `#` 开头的行和空行会被忽略
- 格式不合法的行会跳过并在控制台打印警告，不会中断整个运行
- 「歌手名」只用于显示和日志。改名字不影响新增判定（判定只认专辑ID）
- 歌手ID 重复的行会跳过并提示

## 数据来源与判定规则

网页版 HTML 里已经不再包含专辑数据了，所以这里不用 BeautifulSoup 解析网页，直接调公开接口：

```text
GET https://music.163.com/api/artist/albums/{歌手ID}?offset={offset}&limit={limit}
```

请求头用普通浏览器 UA + `Referer: https://music.163.com/`，超时 15 秒。
每页之间随机延时 1.5~3.5 秒，歌手与歌手之间 5~10 秒。

- `code=200` 且 `artist` 非空 → 本次成功，从 `hotAlbums` 里取 `id` / `name` / `publishTime`（毫秒时间戳转 `YYYY-MM-DD`）
- `code!=200` 或 `artist` 为 `null` → 歌手ID无效，状态记 `invalid`，**不重试**，旧快照不动
- `code=200`、`artist` 非空但 `hotAlbums` 为空 → 视为该歌手没有专辑，状态 `ok`，旧列表清空，不写失败日志
- 翻页：`offset` 从 0 开始、每次 `+= limit`；本页数量 `< limit` 即到达末尾（数量等于 `limit` 才继续翻）
- 网络类错误（超时 / 连接失败 / 5xx）：重试 2 次（间隔 2~3 秒），仍失败则状态记 `failed`，旧快照保留

## 注意事项

- `专辑快照.json` 和 `监控日志.log` 是唯一的历史记录来源。**删掉快照之后，下一次运行会把所有专辑当成新增重新记录一遍**，所以别随手删
- 抓取失败时旧列表会被原样保留，所以偶尔漏跑一次不会丢数据，等下次成功会自动补记
- 日志里的失败原因超过 200 字会被截断，完整原因保存在 `专辑快照.json` 里
- 歌手很多时一次完整运行要几分钟（延时是故意的，别调太小）
- 只读取公开接口，不登录、不下载音频文件
